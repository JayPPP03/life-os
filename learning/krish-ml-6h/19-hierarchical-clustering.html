🤔 Why this formula — feel the intuition

🎯 The business problem: Same Marketing ask — segment the customers into campaign tiers — but this time nobody even knows how many tiers exist, and the dataset is small enough to afford a slower method. Hierarchical clustering is the honest answer: start with every customer alone (100 customers = 100 one-person clusters), merge the closest pair, one merge per round, and write down every merge distance. The number of segments falls out of the data instead of being guessed up front.

🧠 Why THIS formula:

  • The distance matrix — the full n×n map of "who is closest to whom" (every pairwise Euclidean distance). Clustering without it would be like merging companies while knowing none of the valuations: the first merge (smallest cell, P4–P5 at 1.0000) is obvious, but every later merge depends on the map being complete and updated. Skip standardizing features first and the widest-range column writes the whole map by itself — the tree becomes that one feature in disguise.
  • Single linkage = MIN distance between members — once two customers merge, you no longer compare points, you compare CLUSTERS, and single linkage defines "how close are these two groups" as the distance between their closest members: literally "these two groups touch". Pick complete linkage instead and the same data merges in a different order — not wrong, just a different definition of "close", which is why you must state which linkage produced the tiers.
  • Dendrogram heights = merge distances — each join's height records HOW FAR apart the two merged groups were. Short joins are obvious mergers (near-twin customers); tall joins are reluctant ones. That is why you cut where the jump is biggest: everything joined below the cut is genuinely similar, and the tall final merge (4.24 vs 2.06 in the worked run) is the wall between real segments. Cut carelessly and you can present 5 tiers when the data screams 2 — Marketing builds 5 campaigns for 2 real groups.
  • Why greedy merging is the price: every merge is locked in forever — an early bad merge can never be undone later. That greed is also what makes the method slow and brittle as data grows, which is exactly why a 100K+ profile segmentation job falls back to k-means for speed.

📈 See it:

💬 Feel it: Villages merging into a country: neighboring villages join first (cheap mergers, low on the tree), and the final union of two whole regions happens only at a huge "distance" (the tall top join). Read the tree bottom-up and the natural provinces announce themselves — cut between the biggest jumps and you have the tier map Marketing wanted, K included for free.

🔗 This intuition powers everything below.

📋 Coach's Review

Common learner gaps in this topic — check yourself against each before the quiz:

① Confusing dendrogram HEIGHT with a data value.
The height of a join is the merge DISTANCE between the two clusters — it is not a spend value, not a coordinate, not a count.
② Comparing points when you should compare clusters.
After the first merge, the algorithm compares CLUSTERS. With single linkage that means the MINIMUM distance between any member of each — skip the matrix update and every later merge is wrong.
③ Assuming K must be chosen in advance.
That is k-means' requirement. Hierarchical clustering's headline advantage is reading K off the dendrogram — no pre-chosen K.
④ Miscounting clusters after the cut.
The number of clusters = the number of vertical lines the horizontal cut CROSSES — not the leaves, not the merges.
⑤ Running it on raw, unscaled features.
One wide-range feature dominates every distance in the matrix and the whole tree is garbage. Standardize first.
⑥ Treating merges as reversible.
Agglomerative merging is greedy: an early bad merge is locked in forever — one reason large, noisy datasets prefer k-means (topic 18).

✍️ Solve on Paper — Hierarchical Clustering

Close the laptop. Pen and paper. The code works because this math works.

The recipe (agglomerative, single linkage):

  1. Start: n points = n clusters; fill the n×n distance matrix (on a number line: d = |xᵢ − xⱼ|).
  2. Merge the pair with the SMALLEST off-diagonal distance.
  3. Update the matrix: single linkage — distance to the new cluster = MIN distance from any of its members.
  4. Repeat merge → update until one cluster; write down every merge height.
  5. Read the dendrogram: cut through the longest un-crossed stretch; vertical lines crossed = number of clusters.

📝 Notes

The big idea: agglomerative = bottom-up

This section covers agglomerative hierarchical clustering, which builds clusters bottom-up: every point starts as its own cluster (n points → n clusters), and the algorithm repeatedly merges the two closest clusters, one merge per round, until a single cluster remains. Each merge reduces the cluster count by exactly one — n becomes n-1, then n-2, and so on down to 1 — so the whole run is one long merge sequence.

ELI10: nearby villages merge into towns, towns into cities, cities into one country — and every merger gets written down in the family tree.

The dendrogram

That family tree is the dendrogram: it records the full merge history. Each leaf is a single point; every horizontal join is one merge event, and its height shows how far apart the two merged clusters were. Short joins = obvious merges; tall joins = reluctant ones. Cut the same tree at different heights and you get different cluster counts from one run — one cut, one clustering. The dendrogram is the artifact hierarchical clustering gives you and K-means does not.

Choosing the number of clusters (no pre-chosen K!)

The headline advantage: you do not need to pre-choose K. Instead, scan the dendrogram for the longest vertical line that no horizontal line crosses, and pass a horizontal cut through it. The number of vertical lines the cut crosses = the number of clusters. Intuition: that long un-crossed stretch is the biggest jump in merge distance — everything merged below the cut is genuinely similar, while the branches joined above it are truly different groups.

The cost: time

Hierarchical clustering is more time-consuming than K-means on large datasets — the merging keeps comparing cluster pairs as data grows — so it is typically used on smaller datasets. On big data, K-means is the speed pick (topic 18).

💡 Interview angle: Why ever pick agglomerative over K-means? Two reasons from this section: no need to pre-choose K, and the dendrogram hands you a whole family of clusterings you can cut at different levels. The counterpoint? Time — on large datasets K-means wins, which is exactly why big segmentation jobs use K-means.
